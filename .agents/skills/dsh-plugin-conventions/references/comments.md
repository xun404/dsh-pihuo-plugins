# 代码注释

本仓库的代码要能离开作者被读懂。注释写**合同与约束**，不写执行过程。语言：**英文**（与 harness 一致）。产品文案仍是中文。

## 必须写

| 位置 | 写什么 |
|---|---|
| 每个源文件模块顶 | 这个文件在分层里干什么、明确不干什么 |
| 每个 `export` | JSDoc：做什么、输入/输出、失败怎么表现、调用方必须遵守的约束 |
| `Config` 每个字段 | 默认值、单位、省略时的行为 |
| Provider / Driver / 池 | 生命周期：谁 spawn、谁 dispose、取消从哪条信号进来 |
| 协议映射 | 两边名字对照，未知值落到哪一个失败态 |
| 非显然的 `//` | **为什么**这样，或「若改掉会破坏什么」 |

`apply`、`inject`、`name`、公开类型、错误码、复用键字段，全部按导出符号处理。

## 不准写

- 复述标识符：`// increment i`、`/** The name. */`。
- 控制流旁白：`// first we check`、`// then we spawn`。
- 过期叙事：`// used to`、`// temporary until`（期限进 HANDOVER，不进源码）。
- 把规范再抄一遍进注释。规范在技能里，注释只写**这一处**的合同。

## 准确

注释与代码冲突时，**改注释或改代码，不能不理**。审查把过时注释当错误，不当风格建议。

断言的事实必须可核对：默认值、单位、哪条信号、哪次 dispose、未知 stopReason 映射到 `error` 而不是 `completed`。拿不准就别写。

## 完整的标准

读完导出 JSDoc，不打开函数体也应知道：

1. 何时可以调用、需要哪些服务已 `inject`。
2. 成功返回什么；失败是 throw 还是 `stopReason`。
3. 谁拥有子进程 / 会话 / 监听器，谁负责拆。
4. 哪些值进会话日志、哪些只进 `presentationMeta`、哪些禁止 `append`。

做不到这四条，注释就不算完整。
